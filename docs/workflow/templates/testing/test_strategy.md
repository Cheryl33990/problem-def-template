# 測試策略範本 

> **範本庫文件**：需要時才複製到專案紀錄區。本檔連結供瀏覽範本；複製後須改為實際專案文件，未建立的依賴標待建立或連到 brief。做法見 [使用指南](../../guide.md)。

> 衍生時改 draft，填入實際專案工具與指令。本模板內建文件驗證 CI，應用程式的測試與 CI 依專案設定。

核心邏輯、介面組合、使用流程可分層檢驗；選擇依成本與風險。文件或非程式專案可人工驗證。
覆蓋率若有用才訂目標；不能取代失敗、邊界與重要行為驗證。

- 修正可重現的缺陷時，用同一個回歸案例和可觀察判準驗證修正前後。舊版本應因目標缺陷失敗，修正後應通過，同時保留適用的原有行為。若舊版本無法重跑，記錄限制和已有證據。
- 依風險選擇能看見錯誤的入口。單元測試可驗證模組契約，整合問題從實際使用入口跑。確認斷言能辨識錯誤輸出、狀態或副作用。
- 新增自動檢查時，用已知錯誤與有效案例測檢查本身，記下診斷及可能誤報。是否設為合併門檻，由負責人依結果與既有規則決定。

### 依風險選用屬性測試與形式化驗證

先從 AC 或介面契約挑一條可判定的規則，寫明它何時適用、要觀察什麼、怎樣算違反。例如「當回覆標記為有依據時，每個引用 ID 都必須屬於本次檢索結果」。保留已知問題的固定回歸案例。當輸入或狀態組合留下重要風險，再選下表中最直接的測法。小型任務可直接在 brief 或 progress 記錄。

| 剩餘風險 | 選用方法 | 可取得的證據與範圍 |
|---|---|---|
| 邊界輸入、資料組合太多 | **程式屬性測試**。生成合法、未知、混合及空集合等案例，從實際函式或服務入口檢查規則 | 可重現的失敗輸入及本次實際涵蓋的案例。記輸入生成範圍，確認適用條件確實觸發 |
| 問題出在點擊、切換、重新整理或回應抵達的順序 | **UI 屬性測試**。在可重設的測試環境，以 [Bombadil](https://antithesishq.github.io/bombadil/browser/1.2-how-it-works.html) 探索操作。例：切換對話後，先前請求的遲到回覆應留在原本對話 | 涵蓋本次走過的瀏覽器狀態和操作。保留違規軌跡、重跑選項與前置條件。先確認走得到關鍵操作與狀態 |
| 並行、重試或版本切換的順序複雜，造成的錯誤代價高 | **模型檢查**。用 [TLA+／TLC](https://lamport.azurewebsites.net/tla/tools.html) 定義狀態、事件和不變條件。例：請求在索引切換前後，檢索與引用仍使用同一版本 | 模型反例，或指定模型、初始條件與範圍內的檢查結果。保留模型設定與假設，另以實作測試確認關鍵行為符合模型 |
| 關鍵演算法有精確規格，且需要涵蓋所有滿足前提的輸入 | **機器檢查的證明**。例如用 [Lean](https://lean-lang.org/) 證明過濾函式輸出的 ID 都屬於允許集合 | 針對寫明的定理與假設成立。記錄已證明的實作或模型，以及它和交付程式的對應 |

缺乏採用證據時，先以一條規則做限量試跑。用明確違規和有效案例檢查判準，並確認生成器或操作能到達規則適用的狀態。失敗時保留可重現的輸入、操作軌跡或模型反例，能穩定重現的錯誤納入固定回歸。探索性檢查可先在本機或非阻擋 CI 執行，記錄耗時、誤報與需人工介入的原因，再由負責人依穩定性和風險決定是否設為合併門檻。

## 3．規格與結果
每條 AC 使用 [acceptance_tests/TEMPLATE.md](acceptance_tests/TEMPLATE.md) 建規格。執行後用 [validation/TEMPLATE.md](validation/TEMPLATE.md) 保存被測版本、步驟、結果與限制。
程式測試放實際 tests 目錄；規格與結果目錄只放文件。精簡模式可合併，但仍須分清預期與觀測。

## 4．失敗處理
Draft 分支可保留失敗結果供診斷；不得把失敗或 skip 宣稱通過。正式交付必要 AC 未達標就回到實作或需求確認。
flaky 測試記重現條件與 issue，不靠重跑一次綠燈掩蓋；暫時停用須附原因、風險、負責人與恢復計畫。
變更後重跑受影響項目；擴大驗證以未解風險為依據。修門檻先取得確認並保留原結果。
