# 專案工作流程與責任

本文件保存詳細協作規則；階段導航與最小產出以使用指南的階段表為主來源；[使用指南](../guide.md) 是操作指南，[slot contracts](slot_contracts.md) 管單份文件內容，[REVIEW](review.md) 管審查。起始只需 brief 與 progress；以下工件是按需要展開的內容角色，不是必須預建的資料夾。

## 從模糊目標開始：AI 協助釐清

使用者只需描述困擾或期待，不必先定義範圍、非目標、數字指標或完整 PRD。AI 負責把描述整理成可判斷的提案，使用者判斷是否符合需求；「不知道」是有效回答。

1. **接住原始描述**：保存使用者原話，整理已知事實、推測原因、未知與期望，先用白話回述供修正。目標中的工具名稱不自動等於已確認方案。
2. **找具體情境**：優先讀已提供資料；每輪只問最影響下一步的 1–3 題，例如最近一次發生什麼、目前怎麼處理、哪種結果最不能接受。不要求使用者填完整表格或解釋技術名詞。
3. **提出問題與邊界草案**：AI 提一個建議方向，必要時提供 2–3 個有差異的選項。寫清本輪做什麼、暫不做什麼、理由與代價，讓使用者可以修改、接受或表示仍不知道。
4. **協助定義成功**：先問「改善後你會看到什麼不同」，用實際任務、可觀察結果、失敗例子或前後比較草擬標準。不必一開始就量化；可人工判定但要有明確判準。數值門檻無依據時標未知，先提量測基準的方法，禁止憑空填 90% 等數字。
5. **需要時先探索**：使用者仍無法選擇，或缺資料／基準時，提出最小探索任務：要回答的疑問、資料或操作、時間／資源上限、預期交付的發現，以及如何決定下一步。經授權即可執行，不要求先確認整個產品 AC。探索完成不等於產品驗收通過。
6. **整理可確認提案**：摘要問題、範圍、非目標、成功條件、理由與殘餘未知，指出本次要確認的具體內容。取得明確回覆或已有明確授權才標已確認；不能從沉默、文件寫完或 AI 自查推定同意。
7. **迭代**：把已確認內容連到 PRD 與 AC，才開始對應的正式實作；發現衝突時回到本流程修訂，不要求一次把整個專案定死。

### 定義成熟度，逐項記錄

| 成熟度 | 意義 | 可做什麼 |
|---|---|---|
| 未知 | 缺資訊或尚無法判斷 | 蒐集情境、提出探索方法 |
| 暫定 | AI 或使用者提出的候選，尚未接受 | 比較、試探、做已授權的限量探索 |
| 已確認 | 使用者明確接受或先前指示已明確涵蓋 | 作為本輪實作與驗收依據 |

這是問題、範圍或標準的成熟度，不新增 frontmatter status，也不代表測試結果。每項附來源／理由、確認人與日期或待解方式。草案保留 draft；尚有未知不妨礙先確認一個小範圍。會影響該實作安全或成敗的關鍵未知，須先解答或明確接受風險。

例如「資料很多，想更容易找到答案」：先問最近一次找不到的問題；再提「先選一類資料，確認能找回支持答案的原文」的暫定範圍。資料未選定時先做資料盤點，不替使用者決定檢索準確率門檻。

## 四種不同的確認

| 名稱 | 回答的問題 | 保存位置 |
|---|---|---|
| 假設驗證 | 值不值得做、方法是否可能有效？ | discovery、EXP |
| 測試 | 實作是否符合已定義行為？ | test plan、程式測試與驗證紀錄 |
| Review | 問題、設計、變更與證據是否有遺漏或風險？ | PR 或 review 紀錄 |
| 驗收 | 這次範圍是否達到 AC，可以交付嗎？ | AC 對照與完成清單 |

測試通過不等於需求值得做；review 通過不等於所有 AC 已達標；PR 合併不等於已部署或結案。

## 工件分工與單一來源

起始時 PRD、範圍與 AC 合併在 [brief](../../project/brief.md)，小型探索與結果也可就地記錄。只有需要獨立維護時才依指南拆分，progress 登記主來源。


- PRD：問題、需求、成功指標、範圍與約束；修訂記錄解釋目標變更。
- acceptance：AC-NN 與事前確認的通過門檻，避免事後降低標準。
- discovery／EXP：事實、方法與假設結果；不能把推測當證據。
- options／ADR／design：比較、採用的重大決策、實作契約。
- test plan：如何測；[validation 範本](../templates/testing/validation/TEMPLATE.md)：何時對哪個版本測過、結果與限制。
- [work log](../../project/progress.md)：目前做哪件事、阻礙與下一步，不重複保存測試全文。
- [風險與假設](../templates/meta/risks_and_assumptions.md)：尚未消除的不確定性及處理方式。
- Issues：待辦與討論；PR：一批具體變更及審查。不將 issue 關閉或文件 approved 當作 runtime 證據。

## 各階段的進入與完成條件

統一查看 [方法論全圖與階段表](../guide.md#method-map)，此處不另維護一份條件表。階段表列出最小產出、拆分文件時機、前進條件及未達時的處理。

以 [progress](../../project/progress.md) 記錄每個本輪任務的階段、證據與前進判斷。任何階段都能做已授權探索；不確定結果可接受，但不能因此宣稱產品驗收成功。條件已滿足且在既有授權內時持續工作，不逐階段重複索取批准。

## 人與 AI 的分工

專案負責人可同時是使用者與合併者；AI 可協助起草、實作、測試與找問題。AI 的自我檢查不冒充獨立審查。
需要確認的是：對應正式實作的本輪範圍與 AC、重大架構或成本變更、對外發布與合併。已授權範圍內的可逆工作可持續執行，不必逐檔再問。
範圍／AC 變更先說明原因與影響，再取得負責人確認；保留原門檻與本次結果。

## 每次工作循環

1. 讀現有 PRD、AC、相關 ADR、work log；若仍模糊先依上方流程協助釐清，不要求文件完整才開始。只挑一個可檢查的小目標。
2. 用 Issue 或 work log 記目標、對應 AC、範圍與測法；探索尚無產品 AC 時，記疑問、限量範圍與完成條件。建立工作分支。
3. 依需求做探索或實作，先定測法再執行；同步證據與追溯。
4. 開 PR，依 REVIEW 檢查 diff 與測試證據；修正後重驗受影響項目。
5. 合併後更新 work log；需要 runtime 驗證就另跑並保存結果。下一輪繼續，不因一次 PR 就宣告整個專案完成。

## 適用規模

精簡工作可將 PRD、AC、探索、決策與結果合併一份；完整工作依資料夾展開。在 work log 宣告選用哪些文件與 N/A 理由。
原 repo 已有 src、tests、docs 時沿用原結構，記錄路徑對照，不搬移程式或覆蓋既有規則。
本模板沒有安裝 CI、測試工具、保護分支或部署服務；每個衍生專案須另選工具與寫入實際指令。
