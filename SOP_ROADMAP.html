SOP 使用路線圖

遇到新問題時，從這裡開始判斷該走哪條路
適用對象：使用 problem-def-template 衍生新專案的人 日期：2026-05-20 版本：v0.2.0 對應

0. TL;DR

不論你對問題熟不熟，最終都會走完整 SOP（10 → 70）。差別只在「前期投資在哪」—— 熟悉的人把時間花在 10_problem 把問題講清楚； 不熟悉的人把時間花在 20_discovery 把資料讀進去。 選錯起點不會壞事，但會繞遠路。

關鍵原則：三條路最終都會匯流到同一條主線。選錯起點不會壞掉你的專案，但會讓你前 1-2 週做白工。 所以開工前花 5 分鐘評估熟悉度，比「直接做」更有效率。

3. 三條路徑的詳細展開

路徑 1 PRD-first（熟悉路線） 你能描述「為什麼做、做什麼、給誰、怎麼算成功」

Today（30 分鐘）

  • 替換 <PROJECT_NAME> 與 <PROJECT_GOAL> placeholder
  • 更新 README.md / CLAUDE.md / CHANGELOG.md 三檔開頭
  • 把支撐用資料路徑記到 99_meta/data_inventory.md（如有）

Week 1：填問題定義

  • 10_problem/PRD.md §1-7 全部填完（§7 開放問題若超過 5 條，請考慮退回路徑 2）
  • 10_problem/stakeholders.md 至少列 3 個關鍵角色
  • 10_problem/non_goals.md 4 大類至少各列 1 條
  • 10_problem/acceptance.md PRD §4 每條成功指標都有對應驗收條件

Week 2 起：進主線

  • 跳過 20_discovery/（或留作「補充參考」），直接進 25_approach/
  • 把 PRD 內已知的候選方法寫進 options.md、對比寫進 tradeoffs.md
  • 結論變 ADR，進 30_decisions/
退回訊號：填 PRD 時發現自己每寫一段就要查資料、§7 開放問題列越來越長、 對「使用者實際工作流程」說不出具體場景——那你其實在路徑 2，請坦白承認。
路徑 2 Hybrid（半熟路線） 大方向清楚、細節要從資料釐清

Today（30 分鐘）

  • 同路徑 1 的 Today 三件事
  • 把資料納管到 99_meta/data_inventory.md
  • 寫「暫時版」<PROJECT_GOAL>——之後 discovery 會改

Day 2-3：PRD 草稿（容忍空格）

  • 10_problem/PRD.md 把 §1-4 能寫多少寫多少
  • §7 開放問題大量列出——每條都標「預計由哪份探索筆記回答」
  • PRD 維持 status: draft，不要急著升 in-review

Day 4-7：Discovery 補資訊

  • 依 §7 開放問題在 20_discovery/ 建對應筆記（一條問題不一定一份筆記，可合併）
  • 每讀完一輪同步更新 99_meta/glossary.md 新術語
  • 每份筆記寫到 對下一階段的影響 一段時，回頭把對應的 PRD §7 開放問題消掉

Week 2：PRD 升級

  • §7 開放問題清空（或剩 1-2 個「實驗驗證」型問題進 60_experiments/）
  • PRD status 升 in-review，找 stakeholder 對齊
  • 進 25_approach/，主線繼續
路徑 2 的甜蜜點：大多數真實專案都是這條。PRD 與 discovery 互相滋養—— PRD 給 discovery 方向感，discovery 給 PRD 真實感。
路徑 3 Discovery-first（不熟路線） 對領域陌生，資料是原料

Today（30 分鐘）

  • 確認資料夾在 .gitignore 內（公司內部資料尤其重要）
  • 建 99_meta/data_inventory.md：是什麼、來源、機敏性、路徑
  • 替換 placeholder；<PROJECT_GOAL> 寫「暫時版」（給 discovery 一個方向感）

Day 1：規劃 4 份起手筆記

  • 20_discovery/01_corpus_overview.md — 全貌：幾類、結構共通 / 差異、品質
  • 20_discovery/02_domain_concepts.md — 領域術語（同步餵 glossary）
  • 20_discovery/03_current_workflow.md — 現況人工流程、痛點
  • 20_discovery/04_problem_candidates.md — 提煉「可能的問題定義」候選
  • 同步更新 20_discovery/README.md 的目錄表

Day 2-5：系統性讀資料

  • 不要照順序硬讀——依筆記主題挑著讀（01 翻每份只看封面 / 目錄；02 細讀代表性 3-5 份）
  • 每份筆記四段結構：問題 → 方法 → 發現 → 對下一階段的影響
  • 每讀完一輪都餵 99_meta/glossary.md 新術語

Day 6-7：寫 PRD（這時候才寫）

  • 從 04_problem_candidates.md 選 1-2 個 candidate 寫 PRD §1-4
  • 被排除的 candidate 進 non_goals.md
  • PRD status: in-review，找 stakeholder 對齊後升 approved

Week 2 起：進主線

  • 進 25_approach/ 比較候選方法
  • 後續流程同三條路
退回訊號：discovery 寫了一週還沒收斂、04_problem_candidates 列不出 2 個 candidate， 通常是方向感太弱——回頭跟 stakeholder 對一次「大概想解什麼樣的問題」， 把那個粗略方向當錨點再繼續 discovery。

4. 主線骨幹：三條路匯流後的 SOP

不論從哪條路徑進來，後半段都走同一條主線：

10_problem/
問題定義
PRD + stakeholders + non_goals + acceptance。產出物：可驗證的 DoD。
20_discovery/
探索筆記
依主題寫筆記，提煉事實。路徑 1 可跳過；路徑 2/3 的主場。
25_approach/
候選方法比較
options 列方法、tradeoffs 用一致維度評。產出物：給 ADR 用的對比結論。
30_decisions/
ADR
把 25 的結論寫成決策。封存後不修改——要改新增 ADR + 標 deprecated。
40_design/
技術設計
tech_spec + schema + pipeline + prompts。依 ADR 具體化。
45_test_plan/
測試規畫
test_strategy + fixtures + acceptance_tests。先於程式碼存在（TDD）。
50_implementation/
實作
寫程式 + 跑測試。對齊 40 設計；不一致時先改設計再改實作。
60_experiments/
實驗（穿插）
隨時驗證假設。不是線性階段——任何階段需要時都可開 EXP-NNN。
70_closure/
結案與復盤
done_checklist 全勾 + retrospective 寫完。專案才算完成。
圖 3：主線骨幹九階段（99_meta 為跨階段共用）

5. 何時退回上一階段

線性流程是理想；真實工作會有「發現前一階段沒做好」的時刻。下面是常見退路：

觸發訊號 退到哪 具體動作
寫 PRD 寫到一半，§7 開放問題越列越多、§1-4 寫不下去 20_discovery/ 把問題轉成探索筆記主題，補完再回頭升 PRD
25_approach options 寫不出 2 個合理候選 20_discovery/ 對「可行性」做專題探索筆記，補完再回 25
30_decisions ADR 寫到一半發現方法選錯 25_approach/ 重新評估 tradeoffs（不要硬寫一個自己不信的 ADR）
45_test_plan 寫測試規格時，發現驗收條件根本無法測 10_problem/acceptance.md 修驗收條件（可能連帶修 PRD §4），再回 45
50_implementation 實作到一半發現設計撐不起需求 30_decisions/ + 40_design/ 新增 ADR 改路線 + 修 tech_spec（不要在 src/ 偷偷改設計）
退路不是失敗，是 SOP 的設計功能。frontmatter 的 status 與 ADR 的「新增不修改」原則， 就是讓你能誠實退回去而不破壞紀錄。

6. 橫切原則（全程適用，不限階段）

① glossary 隨時更新。新術語先進 99_meta/glossary.md 再被引用—— 不要等寫完一份筆記才補。命名一旦分歧、後續所有文件都要對齊。
② 60_experiments 隨時穿插。不是線性階段——當你想驗證「某個假設真的成立嗎」， 開一個 EXP-NNN 跑。實驗結論再回頭影響 ADR 或 PRD。
③ ADR 不修改只新增。30_decisions/ 已 approved / archived 的 ADR 不可直接動， 要改新增一份、舊的標 deprecated 並用 related 互相連結。 （CLAUDE.md §3 第一條禁令）
④ 所有 .md 必有 frontmatter。三必填（title / status / updated）+ 三選填（owner / tags / related）。 變更檔案時更新 updated: 為當天日期。
⑤ 原始素材不進 git。公司內部 PDF、機敏資料、大型輸入檔—— 路徑記在 99_meta/data_inventory.md，檔案本體放 .gitignore 排除的路徑。
⑥ 追溯矩陣是健康度檢查。99_meta/traceability.md 任何空白欄都是斷鏈警示—— 表示某條 PRD 指標沒有對應實作或測試。結案前必須全部對齊。

7. 常見錯誤與對策

錯誤 為什麼會發生 對策
不熟卻硬走 PRD-first 急著「開始做事」、覺得 discovery 在拖時間 承認 §7 開放問題列太長就退到 discovery；PRD 寫得不準會浪費後面所有階段
discovery 沒收斂 沒有「暫時版 PROJECT_GOAL」當錨點，讀資料失焦 路徑 3 的 Today 一定要寫暫時版 GOAL；發現方向錯了再改
跳過 25_approach 直接寫 ADR 覺得「方法很明顯就一種」 強迫自己列 1 個被否決方案；只有 1 個合理方法時可省 25，但 ADR 的 Alternatives Considered 要寫
實作完才寫測試 覺得測試是「補上去」的東西 45_test_plan/acceptance_tests/ 的規格要先於程式碼存在；用 spec / impl / passing 三段狀態追蹤
專案做完不寫 retrospective 「下個專案要開始了」 done_checklist 全勾後 1-2 週內必寫；對 template 的改進建議寫進 retrospective §7

8. 何時這份路線圖會過時

這份路線圖反映 v0.2.0 的 template 結構。下列情況請更新本檔：

  • 新增 / 移除階段資料夾（例如未來如果加 15_research 或 55_review）
  • 主線匯流點改變（例如三條路在更早或更晚的階段才匯流）
  • 橫切原則新增（例如未來加「risks register 隨時更新」）
  • 跑過一個真實專案後發現「描述的工作流程」與「實際的工作流程」有落差
本檔的本質是「使用說明」，不是「規範」。 規範在 CLAUDE.md 與 99_meta/conventions.md，本檔的角色是把規範翻成「我下一步該做什麼」。
